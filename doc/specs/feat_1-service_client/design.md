# Design

## Overview

Фича добавляет минимальный учет заявок на обслуживание клиентов в основную EDT-конфигурацию `otusJenkinsExampleEDT`.

Решение строится на стандартных объектах 1С:

- подсистема **СервисноеОбслуживание** для отдельного раздела командного интерфейса;
- непроводимый документ **ЗаявкаНаОбслуживание** для регистрации обращения;
- перечисление **СтатусыЗаявокНаОбслуживание** для фиксированного набора статусов;
- отчет **ЗаявкиНаОбслуживание** для просмотра сохраненных заявок;
- существующий справочник **Контрагенты** как источник клиентов.

Фича не вводит регистры, проведение, маршрутизацию, историю статусов и роли. Это сохраняет объем MVP небольшим и делает задачу удобной для учебного разбора в EDT.

## Architecture

Продуктивная часть решения размещается в основной конфигурации, а не в расширениях `YAXUNIT` или `Колонтитулы`. Расширение `otusJenkinsExampleEDT.YAXUNIT` используется только для автоматических тестов.

Основной поток:

1. Пользователь создает документ **ЗаявкаНаОбслуживание**.
2. В форме документа выбирает контрагента, заполняет описание проблемы и при необходимости комментарий.
3. При создании новой заявки система устанавливает статус **Новая**.
4. При записи документа выполняется проверка обязательных полей.
5. Пользователь открывает отчет **ЗаявкиНаОбслуживание** и просматривает список сохраненных заявок.

Документ и отчет доступны пользователю в отдельной подсистеме **Сервисное обслуживание**.

Для разработки, поиска и проверки используется `edt-mcp`:

- новые объекты и реквизиты создавать через инструменты метаданных EDT-MCP, если они доступны;
- свойства созданных объектов и реквизитов задавать через EDT-MCP, если свойство назначаемо;
- BSL-код читать и изменять через EDT-MCP;
- поиск по исходным кодам выполнять через `search_in_code`, `get_module_structure`, `read_method_source`, `find_references` и другие подходящие инструменты EDT-MCP;
- формы анализировать через `get_form_layout_snapshot` или ближайший доступный инструмент EDT-MCP;
- тесты запускать через `run_yaxunit_tests` после выбора launch-конфигурации через `list_configurations`;
- после изменений метаданных, BSL и тестов проверять проект через `get_problem_summary` или ближайший доступный инструмент EDT-MCP.

Если нужный инструмент EDT-MCP не опубликован или недоступен в текущей сессии, это нужно явно отметить и только затем выбрать безопасный обходной способ с учетом правил проекта.

## Components

### Subsystem.СервисноеОбслуживание

Назначение: выделить функции учета заявок на обслуживание в отдельный раздел командного интерфейса.

Покрывает требования: Requirement 1, Requirement 4, Requirement 6.

Свойства:

- имя: `СервисноеОбслуживание`;
- синоним: **Сервисное обслуживание**;
- подсистема включена в командный интерфейс;
- подсистема содержит документ **ЗаявкаНаОбслуживание** и отчет **ЗаявкиНаОбслуживание**.

Перечисление **СтатусыЗаявокНаОбслуживание** можно также включить в состав подсистемы как технически связанный объект, но отдельная пользовательская команда для него не требуется.

### Document.ЗаявкаНаОбслуживание

Назначение: хранить одну заявку на обслуживание клиента.

Покрывает требования: Requirement 1, Requirement 2, Requirement 3.

Свойства:

- документ непроводимый;
- стандартная дата документа используется как дата заявки;
- документ не формирует движения по регистрам;
- документ доступен пользователю через командный интерфейс подсистемы **Сервисное обслуживание**.

Реквизиты:

| Реквизит | Тип | Обязательность | Назначение |
|---|---|---|---|
| Контрагент | CatalogRef.Контрагенты | Да | Клиент, по которому зарегистрирована заявка |
| ОписаниеПроблемы | String, многострочная | Да | Описание обращения клиента |
| Статус | EnumRef.СтатусыЗаявокНаОбслуживание | Да, с автозаполнением | Текущее состояние заявки |
| КомментарийИсполнителя | String, многострочная | Нет | Дополнительный комментарий по обработке заявки |

### Enum.СтатусыЗаявокНаОбслуживание

Назначение: ограничить список допустимых статусов заявки.

Покрывает требования: Requirement 2.

Значения:

| Имя | Синоним | Назначение |
|---|---|---|
| Новая | Новая | Заявка только зарегистрирована |
| ВРаботе | В работе | Заявка находится в обработке |
| Выполнена | Выполнена | Работы по заявке завершены |
| Отменена | Отменена | Заявка отменена |

### Document Form

Назначение: основной экран ввода и редактирования заявки.

Покрывает требования: Requirement 1, Requirement 2, Requirement 3.

На форме должны быть доступны:

- стандартные поля номера и даты документа, если они используются в проектном шаблоне документов;
- поле **Контрагент**;
- поле **Описание проблемы**;
- поле **Статус**;
- поле **Комментарий исполнителя**.

Для многострочных полей нужно выбрать представление, удобное для ввода текста. Специальные команды, табличные части и отдельные страницы формы в MVP не требуются.

### Report.ЗаявкиНаОбслуживание

Назначение: показать список сохраненных заявок на обслуживание.

Покрывает требования: Requirement 4.

Рекомендуемый способ реализации для MVP: простой отчет на СКД с одним набором данных-запросом. Отдельный BSL-код отчета не требуется, если отчет можно собрать средствами схемы компоновки данных.

Минимальный состав результата:

| Поле | Источник |
|---|---|
| Номер | Document.ЗаявкаНаОбслуживание.Number |
| Дата | Document.ЗаявкаНаОбслуживание.Date |
| Контрагент | Document.ЗаявкаНаОбслуживание.Контрагент |
| Описание проблемы | Document.ЗаявкаНаОбслуживание.ОписаниеПроблемы |
| Статус | Document.ЗаявкаНаОбслуживание.Статус |

Поле **Номер** добавляется как полезный идентификатор строки отчета. Минимум из Requirement 4 при этом сохраняется: дата, контрагент, описание проблемы и статус.

Отчет должен быть только читающим. На этапе MVP не нужны параметры отбора, группировки, диаграммы и сохраненные варианты. Если стандартные настройки СКД позволяют быстро добавить сортировку, предпочтительно сортировать заявки по дате по убыванию.

### Subsystem Placement

В конфигурации уже есть подсистемы **Предприятие**, **Закупки**, **Продажи**, **Финансы**, **Товарные запасы** и вложенные подсистемы.

Для учебного MVP создается новая подсистема **Сервисное обслуживание**. Это делает фичу заметной в интерфейсе и не смешивает сервисные заявки с существующими разделами продаж, закупок, финансов и товарных запасов.

Состав подсистемы:

- `Document.ЗаявкаНаОбслуживание`;
- `Report.ЗаявкиНаОбслуживание`;
- `Enum.СтатусыЗаявокНаОбслуживание` как связанный объект без самостоятельной пользовательской команды.

Справочник **Контрагенты** используется по ссылке и не переносится в новую подсистему, потому что он уже является общим справочником проекта.

## Testing

В проекте есть расширение `otusJenkinsExampleEDT.YAXUNIT` по пути `src/cfe/otusJenkinsExampleEDT.YAXUNIT`. Для MVP нужно добавить несколько простых YAxUnit-тестов в это расширение. Продуктивные объекты при этом остаются в основной конфигурации.

Тесты должны покрыть серверную бизнес-логику документа, которую можно проверить без UI:

- новая заявка без явно заданного статуса получает статус **Новая** перед записью;
- заявка без контрагента не записывается;
- заявка без описания проблемы не записывается;
- корректная заявка с контрагентом и описанием записывается.

Тестовые данные должны создаваться самими тестами. Если для корректной заявки нужен контрагент, тест должен создать временный элемент справочника **Контрагенты** или использовать безопасный тестовый fixture, уже принятый в расширении.

Тесты должны быть изолированы настолько, насколько это разумно для учебного проекта: не зависеть от ручных данных базы и использовать уникальные наименования тестовых объектов. Очистка созданных данных желательна, но не должна усложнять MVP сильнее самих тестов.

Тесты не заменяют ручную проверку формы и отчета, потому что UI-сценарии и визуальный результат отчета в рамках MVP подтверждаются вручную.

## Behavior

### Default Status

При создании нового документа статус должен автоматически заполняться значением `Перечисления.СтатусыЗаявокНаОбслуживание.Новая`.

Рекомендуемая реализация:

- в форме документа заполнить статус для нового объекта, чтобы пользователь видел значение **Новая** до первой записи;
- в модуле объекта перед записью повторно установить статус **Новая**, если реквизит остался пустым.

Такой подход сохраняет удобство UI и защищает объект при записи не из основной формы.

### Validation

Перед записью заявки нужно проверить:

- заполнен ли реквизит **Контрагент**;
- заполнено ли **ОписаниеПроблемы**;
- если **Статус** пустой, установить **Новая**.

При незаполненных обязательных полях запись должна быть остановлена с понятным сообщением пользователю. Комментарий исполнителя не проверяется.

Валидацию следует размещать в модуле объекта документа, чтобы она срабатывала не только из основной формы, но и при записи документа из других сценариев.

### Report Query

Отчет получает данные из `Документ.ЗаявкаНаОбслуживание`. Для MVP запрос может использоваться как набор данных СКД.

Базовый запрос:

```bsl
ВЫБРАТЬ
    ЗаявкаНаОбслуживание.Номер КАК Номер,
    ЗаявкаНаОбслуживание.Дата КАК Дата,
    ЗаявкаНаОбслуживание.Контрагент КАК Контрагент,
    ЗаявкаНаОбслуживание.ОписаниеПроблемы КАК ОписаниеПроблемы,
    ЗаявкаНаОбслуживание.Статус КАК Статус
ИЗ
    Документ.ЗаявкаНаОбслуживание КАК ЗаявкаНаОбслуживание
УПОРЯДОЧИТЬ ПО
    Дата УБЫВ
```

Перед использованием запроса в реализации его нужно проверить через `validate_query`, когда объект документа уже создан в EDT. Если запрос проверяется как запрос СКД, использовать режим проверки для СКД.

## UI Flow

### Создание заявки

1. Пользователь открывает создание документа **Заявка на обслуживание**.
   Основная точка входа - подсистема **Сервисное обслуживание**.
2. Система показывает форму документа.
3. Статус новой заявки заполнен значением **Новая**.
4. Пользователь выбирает контрагента и вводит описание проблемы.
5. Пользователь записывает документ.
6. Если обязательные поля заполнены, документ сохраняется.
7. Если обязательные поля не заполнены, пользователь получает сообщение и остается в форме.

### Просмотр заявок

1. Пользователь открывает отчет **Заявки на обслуживание**.
   Основная точка входа - подсистема **Сервисное обслуживание**.
2. Система формирует список сохраненных заявок.
3. Если заявок нет, отчет показывает пустой результат без ошибки.

## Risks and Trade-offs

- Отказ от регистра сведений упрощает MVP, но не позволяет хранить историю статусов.
- Использование стандартной даты документа снижает количество реквизитов, но требует явно объяснить это на уроке.
- Отдельная подсистема **Сервисное обслуживание** добавляет один объект метаданных, зато делает учебную фичу видимой и предметно отделенной от существующих разделов.
- Простой отчет без параметров быстрее реализовать и проверить, но он не решает сценарии фильтрации по статусу или периоду.
- YAxUnit-тесты добавляют немного объема к учебной задаче, зато показывают полный цикл разработки: фича, валидация, автоматическая проверка и запуск тестов в pipeline.

## Verification

После реализации нужно проверить:

- `get_problem_summary` по проекту `otusJenkinsExampleEDT`;
- отсутствие ошибок по объектам `Subsystem.СервисноеОбслуживание`, `Document.ЗаявкаНаОбслуживание`, `Enum.СтатусыЗаявокНаОбслуживание`, `Report.ЗаявкиНаОбслуживание`;
- отсутствие ошибок по измененным объектам расширения `otusJenkinsExampleEDT.YAXUNIT`;
- синтаксис BSL-модуля документа после добавления валидации;
- запрос отчета через `validate_query`, при необходимости в режиме СКД;
- запуск простых YAxUnit-тестов через `run_yaxunit_tests` с фильтром по расширению `otusJenkinsExampleEDT.YAXUNIT`;
- ручной сценарий в режиме 1С:Предприятие: создание заявки, ошибка без обязательных полей, сохранение корректной заявки, открытие отчета.
