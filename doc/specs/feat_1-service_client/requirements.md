# Requirements

## Overview

Нужно добавить в учебную конфигурацию минимальный учет заявок на обслуживание клиентов.

Клиенты уже отражаются существующим справочником **Контрагенты**, поэтому отдельный справочник клиентов создавать не нужно. Пользователь должен иметь возможность зарегистрировать обращение контрагента, указать проблему, статус обработки и затем посмотреть список всех заявок в отчете.

Результат фичи - MVP для демонстрации разработки в EDT: создание метаданных, формы, простой бизнес-валидации и отчета. Учет заявок нужен только для регистрации и просмотра обращений, без управленческого процесса обработки заявок.

## User Stories

- Как пользователь, я хочу зарегистрировать заявку на обслуживание по контрагенту, чтобы зафиксировать обращение клиента и не потерять информацию о проблеме.
- Как пользователь, я хочу видеть статус заявки, чтобы понимать, на каком этапе находится обработка обращения.
- Как пользователь, я хочу открыть отчет со всеми заявками, чтобы быстро просмотреть текущий список обращений без поиска по журналу документов.
- Как пользователь, я хочу видеть функции обслуживания в отдельном разделе **Сервисное обслуживание**, чтобы они не смешивались с продажами, закупками и финансами.

## Requirements

### Requirement 1. Регистрация заявки на обслуживание

Система должна позволять пользователю создавать заявку на обслуживание клиента как самостоятельную запись обращения.

#### Acceptance Criteria

- При создании заявки пользователь может выбрать контрагента из существующего справочника **Контрагенты**.
- Пользователь может открыть создание заявки из подсистемы **Сервисное обслуживание**.
- В заявке фиксируется дата заявки.
- В заявке можно заполнить описание проблемы.
- В заявке можно выбрать статус заявки.
- В заявке можно заполнить комментарий исполнителя.
- После записи заявки она сохраняется и доступна для последующего просмотра.
- В рамках MVP заявка не должна требовать проведения и не должна формировать движения по регистрам.

### Requirement 2. Статусы заявки

Система должна поддерживать фиксированный набор статусов заявки на обслуживание.

#### Acceptance Criteria

- Пользователь может выбрать один из статусов: **Новая**, **ВРаботе**, **Выполнена**, **Отменена**.
- Для новой заявки статус по умолчанию устанавливается в значение **Новая** до первой записи.
- Пользователь может изменить статус заявки вручную.
- Пользователь не должен вводить статус произвольным текстом.
- История изменения статусов в рамках MVP не ведется.

### Requirement 3. Проверка обязательных полей

Система должна проверять минимально необходимые данные перед сохранением заявки.

#### Acceptance Criteria

- Если в заявке не выбран контрагент, система не должна сохранять заявку.
- Если в заявке не заполнено описание проблемы, система не должна сохранять заявку.
- При ошибке заполнения пользователь должен получить понятное сообщение о том, какое поле нужно заполнить.
- Если обязательные поля заполнены, заявка может быть сохранена без дополнительных бизнес-проверок.

### Requirement 4. Просмотр заявок в отчете

Система должна предоставлять отчет, в котором пользователь может увидеть сохраненные заявки на обслуживание.

#### Acceptance Criteria

- Пользователь может открыть отчет по заявкам на обслуживание.
- Пользователь может открыть отчет из подсистемы **Сервисное обслуживание**.
- В отчете отображаются сохраненные заявки независимо от статуса.
- Для каждой заявки в отчете отображается минимум: дата, контрагент, описание проблемы и статус.
- Если заявок нет, отчет открывается без ошибки и показывает пустой результат.
- Отчет не должен изменять данные заявок.

### Requirement 5. Автоматическая проверка бизнес-логики

Ключевая серверная логика заявки должна быть покрыта простыми YAxUnit-тестами в существующем тестовом расширении.

#### Acceptance Criteria

- Тесты размещаются в расширении `otusJenkinsExampleEDT.YAXUNIT`.
- Тесты проверяют установку статуса **Новая** для новой заявки.
- Тесты проверяют запрет записи заявки без контрагента.
- Тесты проверяют запрет записи заявки без описания проблемы.
- Тесты проверяют успешную запись корректной заявки.
- Тесты не требуют заранее вручную созданных данных, кроме объектов конфигурации, которые входят в поставку проекта.

### Requirement 6. Раздел сервисного обслуживания

Функции учета заявок должны быть сгруппированы в отдельной подсистеме.

#### Acceptance Criteria

- В конфигурации есть подсистема **Сервисное обслуживание**.
- Подсистема отображается в командном интерфейсе.
- Документ **ЗаявкаНаОбслуживание** доступен из подсистемы **Сервисное обслуживание**.
- Отчет **ЗаявкиНаОбслуживание** доступен из подсистемы **Сервисное обслуживание**.
- Справочник **Контрагенты** не переносится в новую подсистему и остается существующим общим справочником проекта.

## Edge Cases

- Если пользователь создает новую заявку и не выбирает статус, система должна установить статус **Новая**.
- Если пользователь пытается записать заявку без контрагента, запись должна быть остановлена.
- Если пользователь пытается записать заявку с пустым описанием проблемы, запись должна быть остановлена.
- Если в базе нет заявок, отчет должен оставаться работоспособным.
- Если у заявки не заполнен комментарий исполнителя, это не должно мешать сохранению.
- Если в тестовой информационной базе нет подходящего контрагента, YAxUnit-тест должен создать необходимые тестовые данные самостоятельно.

## Assumptions

- Справочник **Контрагенты** уже существует в конфигурации и будет использован как источник клиентов.
- Фактическое наличие справочника **Контрагенты** подтверждено в основном EDT-проекте `otusJenkinsExampleEDT`.
- Дата заявки может быть реализована стандартной датой документа 1С; отдельный реквизит даты нужен только если это будет явно решено на этапе дизайна.
- Требования к правам доступа, ролям и разграничению видимости заявок в рамках MVP не реализуются.
- Маршрутизация заявок, назначение исполнителей, история изменения статусов и SLA не входят в MVP.
- Отчет нужен только для просмотра списка заявок; сложные фильтры и аналитика не требуются на первом этапе.
- Для объектов MVP создается отдельная подсистема **Сервисное обслуживание**.
- Разработка, поиск по исходным кодам, изменение метаданных, изменение BSL-кода и проверки будут выполняться в EDT с использованием `edt-mcp` по правилам проекта.
- Автоматические тесты должны использовать существующее расширение `otusJenkinsExampleEDT.YAXUNIT`; продуктивная логика фичи в этом расширении не размещается.
- Если нужный инструмент `edt-mcp` недоступен в текущей сессии, это нужно явно зафиксировать перед выбором обходного способа.

## Out of Scope

- Создание отдельного справочника клиентов.
- Интеграции с внешними системами.
- Уведомления пользователям.
- Печатные формы заявки.
- Автоматическое назначение ответственного исполнителя.
- Проведение заявок, регистры накопления или сведений для учета состояния.
- Отдельная тестовая инфраструктура вне существующего расширения YAxUnit.
